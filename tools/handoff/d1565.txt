## v15.65 - CTRL WITH THE MOUSE WHEEL SIZES THE HUD WITHOUT TOGGLING CROUCH

Stealth audit finding (MEDIUM), index 3 of the confirmed list in audit-wfxd2t8x2.json. The verdict found it real and gave a
corrected fix, which is the build, with two small additions named below.

In a raid, standing, hold Ctrl and roll the wheel: that is his v9.95 HUD size gesture (and every browser's zoom gesture, which
the canvas listener already prevents). The Ctrl keydown reaches raidKey first, and the v9.92/v10.07 crouch line
if((code==='ControlLeft'||code==='ControlRight'||code==='KeyC')&&G&&!G.over&&!G.sim&&!repeat){ G.crouchTog=!G.crouchTog; }
flipped the toggle. The canvas wheel listener then ran if(e.ctrlKey){ if(e.deltaY!==0) hudSizeStep(...); return; }, which sized
the HUD and never touched the stance, and the keyup listener only cleared the key. Crouch has been a toggle since v10.07, so
letting go of Ctrl did not undo it: sizing the HUD standing left him crouched at .52 speed with the HIDDEN plate up, and sizing
it while crouched in a bush stood him up and dropped the 170 hide rule. The only message was hudSizeStep's HUD size line;
nothing said the stance changed. The two features come from two separate notes of his (v9.92 Ctrl or C crouches, v9.95 Ctrl
and the wheel size the HUD); no comment or ruling mentions the clash. An input bug, not balance.

THE BUILD. Four code edits plus VER and DEVNOW.
1. raidKey, the crouch line (near 11083): before the flip, G.ctrlUndo=(ev&&code!=='KeyC')?G.crouchTog:null; keeps the stance
   from before a keyboard Ctrl press. C is never a modifier and keeps nothing. ADDITION ONE: the controller right stick click
   (v13.36) reaches raidKey as raidKey('ControlLeft',false,null) from pollPad, with ev null, so it keeps nothing either; the
   verdict's version would have kept a stance for a press with no Ctrl key behind it. The flip itself is unchanged, so a plain
   Ctrl press still crouches at once, one change per press (his v13.36 rule).
2. The canvas wheel listener (near 11258): inside if(e.ctrlKey), when G.ctrlUndo is set and a keyboard Ctrl is really held
   (keys ControlLeft or ControlRight), the crouch toggle is given back its stance from before that press; G.ctrlUndo is then
   cleared on every Ctrl wheel, so only the first notch restores and later notches only size. The keys test means a trackpad
   pinch, which sends ctrlKey wheel events with no Ctrl keydown, changes no stance. The HUD step line is unchanged.
3. The window keyup listener (near 11267): a Ctrl keyup also clears G.ctrlUndo, so a Ctrl let go with no wheel stays a plain
   crouch press and a later Ctrl with the wheel cannot give back a stance from an older press.
4. ADDITION TWO, releaseAllKeys (near 29956): if(G) G.ctrlUndo=null; beside the existing bag and drag clear. A Ctrl held when
   the window loses focus (Ctrl+Tab to another browser tab is the common case) never sends its keyup to the game, and the
   verdict names a stale value as the thing to avoid.
Restoring the old stance rather than flipping a second time is the verdict's point: holding Ctrl and then rolling or sprinting
(both set crouchTog=false) before the wheel does not crouch him again from standing. Known gaps, both small: he is crouched for
the few frames between the Ctrl press and the first notch (avoiding it would move crouch to the key release and change when
crouch happens), and if he started crouched, pressed Ctrl, rolled while holding it and then rolled the wheel, the restore puts
him back crouched where the roll alone would have left him standing. No player text was added or reworded (no TXSHIP key is
touched), no number, dial or loot table moved, and no seeded draw was added or reordered; map building is not touched, so the
seed 4242 fingerprint in __verifySafe (ents 85/374, containers 165/593) cannot move. G.ctrlUndo lives on the raid object, so a
new raid starts with none.

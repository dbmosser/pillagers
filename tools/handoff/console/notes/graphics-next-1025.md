## 4K frame budget
Bottom line: the only real 4K measurement is 2.5 days old. It is from the VM on 10-23 between 00:48 and 02:47, build v34.18, with two 4K windows (the party setup). An average frame takes 6.25 ms of the game's own work, so about 10 ms is free. The slow end is already at or over the 60 fps line: the slowest frame in 20 takes 16.25 ms and the slowest in 100 takes 27.5 ms. So the game can afford effects in an average frame but has no room in busy frames. Nothing has measured 4K since; the game is now on v34.69, 51 versions later.

Why there is no newer 4K data:
(1) On 10-22 at 23:15 the main PC's robot on port 9332 was set back to 1080p. At 4K, Chrome used about 15% of the graphics card, and the main PC's game check read that as him gaming and slowed the VM down (memory note pillagers-main-pc-idle-tests-2026-10-22.md). The one 4K start on the main PC (tools/handoff/spare/JUL26/fuzz.log line 310, 10-22 22:35, v34.18) logged no raids. Every start on the main PC after it is size=1920x1080. The mirror file is identical to the copy on git origin/spare-results, newest 10-25 09:22.
(2) The VM's runner is an old running copy. tools/nightly.sh line 185 now says szarg="-Size 3840x2160", but the "fuzz2 start" lines in tools/handoff/nightly/nightly.log (lines 899 to 961) never say "at 4K". The VM log tools/handoff/fuzz/fuzz.log has only two 4K starts (line 472, 10-22 23:26:57; line 507, 10-23 00:48:36). Every start after 10-23 02:49 is 1080p.

Three things make the numbers less reliable than they look:
(a) The 4K line in tools/handoff/spare-status.txt ("work 5.75 / 11.25 / 14.75, 40 windows, newest 10-23 00:45") is wrong. perf4k() in tools/spare/spare-import.mjs (lines 89 to 99) switches its 4K flag on every FUZZ START line. Two robots log into the same file, so it mixes the 1080p robot's raids in with the 4K ones, and it drops the whole second 4K block after the 1080p start at 00:50:42. Splitting the two robots apart gives 6.25 / 16.25 / 27.5 ms.
(b) The robots never play the pixel look, which is what he plays. The test copy turns it off (tools/mkfixture.ps1 line 129 in __resetCfg and line 134 at load), and fuzz.ps1 never turns it back on. In the game it is on by default (row xfPix, dark_raiders.html line 4190; pixOn at line 51343). The pixel look adds sprite-building work: up to 2 builds or 2 ms a frame (PIXSTORE, line 51344), and the floor is built in pieces of up to 4 ms a frame (PIXG, line 51617), mostly during the ascend countdown.
(c) work= is only the game's own script time per frame: from DRS.frameStart (line 53567) to the end of the HUD (DRS.workMs, line 41914). It does not include the graphics card's drawing or Chrome putting the frame on screen. In the VM a hidden browser gets only about 30 frames a second, so gfx= reads 31.25 ms there and only work= means anything. The VM also runs two robots (up to 4 game windows) beside the helper lanes, so its numbers include that load.

Auto resolution (DRS at line 35429, drsTick at line 35490): when frames are slow it first drops effects in three steps (fewer sparks, then lighter vignette and weather, then two-thirds-size soft sheets; gfxqApply at line 35436). It lowers sharpness only after a measured gain, never below 0.75, in steps of 0.05, and shows "RESOLUTION STEPPED DOWN" (line 35487). Slow means the 1-in-20 frame gap over a 2-second window is above 20 ms. Recovery needs gaps under 17.5 ms and work under 10 ms.
- In the robots it lowered sharpness in 13 of about 2,380 windows (main PC 9 of 1,384, VM 4 of 997). All were 2-player raids, down to 0.75 to 0.9, each with 250 to 1,000 frames over 25 ms.
- The newest step-downs were 10-24 18:08 (main PC, v34.51) and 10-24 18:43 (VM, v34.53). There were none on v34.60 to v34.69.
- In the VM 4K runs it never fired: the scale was 1 in all 70 windows. The 30 fps cap means a softer picture shows no gain, so the step-down cannot fire there. The VM can therefore not test it.
- In his own play (exports/run-20261020-215550-244.txt, very likely his: a 56-run profile with raids from v24.71 to v33.17, 288k XP) the scale dropped in 5 raids before the 0.75 floor existed: 0.8 and 0.7 on v28, 0.5 on v29.09, 0.8 and 0.5 on v30.57. His last raids (v31.82, v33.17) stayed at full resolution.

Which drawing parts cost most: the game's own per-part timer (G.tel.gfx.pass, 1 frame in 15, script time only; marks in render2D at lines 41444, 41606, 41775, 41908, 41911) puts the world pass first, the HUD second and fog third. Light and weather are close to zero.

Combat does not explain the slow frames: shots fired against slow frames correlates at 0.05 over 605 two-player raids on the main PC (0.22 on v34.6x). No probe has measured the graphics card's own drawing time at 4K. The 10-14 4K soak (tools/handoff/soak4k.ps1, one window, about v27.10) held 60 fps lowest and median, but it stood still in each raid.

Headroom: Against 16.7 ms (60 fps) at 4K with two windows (VM, v34.18, 10-23): an average frame has about 10.4 ms spare (6.25 ms used, about 37% of the budget). The 1-in-20 frame has about 0.45 ms spare (16.25 ms; nearly half the windows go over). The 1-in-100 frame is about 10.8 ms over (27.5 ms; 38 of 42 windows go over). So an effect that costs 1 to 3 ms in every frame fits in an average frame but pushes the busy frames further under 60 fps. Effects added now should be cheap in busy moments, or hang off the existing quality steps (sparks are dropped first, then vignette and weather) so the auto step-down can drop them. Three cautions: the number is 51 versions old (v34.18 against v34.69 today); it was taken with the pixel look off, while he plays with it on (its sprite building adds up to 2 ms a frame, and the floor up to 4 ms a frame, mostly in the ascend countdown); and work= leaves out the graphics card's drawing time. Before spending the headroom, restart the VM runner (or start fuzz.ps1 -Size 3840x2160 on 9332) with the pixel look on, and fix perf4k, so there is a current 4K number.

- Full-screen bloom with a blur filter or a downsample chain: At 4K the 1-in-20 frame had about 0.45 ms spare (VM, v34.18), and a full-screen blur costs several ms. The glow-sprite idea gets most of the look for almost nothing.
- Film grain (gfx39): His a37 pick was 'as now'. Noise fights the crisp pixel look, and a full-screen layer at 4K adds GPU fill that work= never measures.
- WebGL, shaders, normal-mapped lighting or a 3D light model: Vetoed: 2.5D Canvas 2D only, no external libraries (CLAUDE.md scope boundary, rule 6).
- Per-frame lamp shadows that trace wall sight lines every frame: Too costly in busy frames, and it would pull sim sight code into the draw layer. The baked per-lamp version is listed instead.
- Bigger muzzle flashes or new tracers: His a33 A pick was 'muzzle flash and tracers as now', and REDUCED FLASHING is on by default by his answer 2.61 (v32.91).
- Actor halos or rim light for TV reading (gfx41): Seat rings, P1 amber and P2 cyan, team-colour shoulders and the dark outline already do this job (his a06 A and a07 A 'as now'). World effects already scale with the 4K zoom.
- Wire up LARGE FOR TV: This is HUD, not the raid world. It has been a parked coordinator question since 10-21 ('wire it or remove the row'), and only he decides.
- BUILD body shapes in the pixel look: His 10-20 cosmetics cut folded a04 C into one body shape.
- Bodies or wreck piles that stay, or ragdolls: Vetoed: bodies never come back (v5.28). Bot death is fall and fade (a23 B).
- See-through or fading walls when a player is behind them: Vetoed by his 09-03 note; the dial has been off since v10.60.
- New weather kinds (snow, sandstorm): That is a new feature he did not order. The weather table is older than 10-12, and his look list does not ask for it.
- Steam vents and ambient embers (gfx36): Steam vents are new map props that must sit on real footprints (FEATURES FIT THE MAP), so they are not a pure effect. Embers already ship on burning bodies and barrel fires (forge8, v28.98).

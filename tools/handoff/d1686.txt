## v16.86 - A TEAMMATE WHO HAS LEFT IS NEVER WAITED FOR

Stability pass before his co-op session. WHAT I CHECKED ON THE HOST WHEN THE GUEST EXTRACTS FIRST. The guest window ends its raid with endRaid -> netUpEnd -> {t:'up',st:'out',how:'extract'}. On the host that word reaches netUpWord (dark_raiders.html ~35852): it does NET.up[s]=null and netSrchEndSeat(s) (lets go of the box he was searching) and passes the word on. Nothing else. No message type in the dispatch (~34998-35035: st, raid, up, en, ent, hit, shot, kill, contact, kitask, sum, kf, png, wp, fx, wd, bcn, rev, aid, srch, loot, cont) writes a ring: the rings are host owned (netWorldSend sends them, netWorldTake only runs on a linked window), so the landed window (z.hold), the beacon (z.beaconT) and G.active/G.beaconT/G.shipHold on the host are untouched by a teammate leaving. The sum word only fills the oc_party panel of the run card. THE DOWNED PATH IS INTACT. updatePlayer has no early return before its downed branch; the branch (15927-15982) crawls, runs the self revive on F and then calls tryExtractTick(dt,!!keys['KeyE']), so E passes through while down. tryExtractTick (15050-15122): inside a landed ring (z.hold>0) a downed man gets the same 1.4 s hold as anyone (CFG.hauledAboard is 0 by default, forced to 0 by the cfgv<11 migration at 2924), the one-time knock-down reset only fires for a pull that began standing (pullFloor), and the hold keeps the window open while pulling (15753). Nothing in that path asks NET. netRevHold (16512) never eats E for a downed player (netMateDown returns -1 when p.downed). Superhot cannot freeze the pull: any held key counts as acting (30729). netAllPaused only matters while G.paused. The host plays only a pad it picked (netPadFor), so the forwarded child pad never touches the host keys; and netPadRecv stamps the hand-over on receipt (at:netPadNow()), so the forward is not a clock problem either. THE ONE PLACE A TEAMMATE WHO HAS LEFT CHANGES THE HOST EXTRACTION. endRaid (20370) does: if(!netSpecStart(how)) netUpEnd(how). netSpecStart (36703) counts netUpShown(NET.up[i]) and, when any teammate reads as up top, parks the host: NET.specG=G, G.player.specOut=1, the party is told spec (not out), NET.status='Your party is still in the raid. Waiting for them to finish.' and the host cannot go up again until netSpecEnd. netUpShown is true for a seat whose entry has n>0, age<NET_HUB_STALE (3 s) and the raid seed. The position words travel on peer.fc, created at 34856 with ordered:false, maxRetransmits:0, while the out word goes on the ordered dc: a last position word can land AFTER the out word and netOnState (35181) files the seat again from scratch (age 0, n 1, sd the raid seed), which v16.70 already recorded in its own words (a last position word on the fast, unordered channel can land after his out word and file him again). So a host who completes his pull while that ghost entry is alive is not let out of the raid: his run is parked spectating for a teammate who has already extracted, and the party is told spec instead of out. That is the only concrete host-side mechanism by which the guest having extracted first bears on the host extraction, and it is reachable exactly in the same-PC two-window case (one pad, one keyboard, localhost WebRTC, the out word and the last position word sent within the same frame). THE FIX. netUpWord marks the seat out on the current raid seed (NET.upOut[s]=NET.upSeed) on every word that is not in, and clears it on in (every ascent broadcasts {t:'up',st:'in'}, 35891); netOnState refuses a word from up top for a seat marked out on that seed (returns 'gone'); netUpEnd clears the marks with the raid. With that, a teammate who has left never comes back as a ghost, netSpecStart counts nobody, and the host extraction, downed or standing, ends the raid outright and tells the party out. What this does NOT cover, said plainly: if his E never reached the host window because the player 2 window had the keyboard focus (his third item), or if the 30 s landed window had already run out before he pulled (the game then says Extraction left without you and a new call cannot beat a 17 s bleed), no code on the host refuses the pull and this fix changes nothing there; the question below separates those cases.
